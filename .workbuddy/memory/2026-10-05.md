### 修复内容（RestarterMain.java + RestarterCommand.java + config.yml）
1. **preventInterrupt 完全失效** → 改为注册 JVM 关闭钩子（`installShutdownHook`），
   不再在 onDisable 里塞调度任务；新增 `launchRestartScript()` 直接 exec restart-script
   （刻意不用 `Server.restart()`，因为它每次都 addShutdownHook、非幂等会重复重启）。
   钩子带 `owner != Joyous.plugin` 守卫，防 PlugMan 热重载后旧钩子重复重启。
2. **计划重启被误判异常关闭** → 引入 `exitIntent` 标记（scheduleStop / performRestart /
   performShutdown 置位，`cancelPlan()` 复位）；`cancelCountdown()` **刻意不清位**
   （否则倒计时结束时先 cancel 再 performRestart 会把标记抹掉）。
3. **假人名册在踢人后才采集 → 每轮清空** → 新增 `saveStateAndKickAllPlayers()`，保存先于踢人；
   4. **命令增删假人不落盘** → `addFakePlayer/removeFakePlayer` 立即 `persistFakePlayers()`；
5. **改为「常驻名册」模型**：`recoverFakePlayers()` 恢复后不再 clear 内存与 dat ——
   名册是崩溃（onDisable 不执行）时唯一的恢复依据。
6. **checkTimeConditions 的 ClassCastException**（YAML `days: [7.2]` 是 Double、
   `dayOfM: [1]` 是 Integer）→ 全部改用 `getInt/getListOfString` 类型化访问器。
7. 时间条件语义改为「时刻字段彼此与 + 日期规则彼此或 + 日期与时刻相与 + 全空不触发」
   （原 OR 语义让默认配置变成"每分钟一次"，已在 config.yml 写明新语义）。
8. 重启脚本未配置时真正回退为关闭（原来只打日志、什么都不做）。
9. 泄漏检测：原公式在"整体上涨"前置判断下恒为负、必然触发 → 改为取窗口内
   **最后一次 Full GC 的前后采样对**计算回收率。
10. 堆转储移到独立线程 + 完成后才重启（否则 JVM 退出会留下截断的 .hprof）+ `heapDump.keep` 保留份数。

## 追加：内存泄漏检测实测（结论：不生效）

用 /tmp/leakprobe 下的一次性探针（Java 24 + G1，-Xmx512m，复刻 RestarterMain 的判据、时间尺度压缩 20 倍）实测：

1. **线上根本没跑**：`mcserver/plugins/Joyous/config.yml` 的 `autoRestart.timeout = -1`，
   `startMemoryCheck()` 因此不启动；latest.log 里也没有"内存检测已启动"这行。
   运行期 while 段还是旧结构（只有 `oomPercent`），缺 checkInterval/oldGenPercent/leakDetection 等键。
2. **即使打开，泄漏检测也是死分支**：判据第 2 条要求"窗口内 GC 计数变化"，而
   `getFullGCCount()` 只统计名字含 old/marksweep/zgc/shenandoah 的收集器。现代 G1（JDK 14+）
   把并发周期拆到了独立 bean `G1 Concurrent GC`（名字不含上述关键词 → 不计入），
   `G1 Old Generation` 只在**真正的 Pause Full** 时递增。
   实测：老年代涨到 482MB/512MB(94%)、Mixed GC 2 次、Concurrent GC 计数 202，`G1 Old Generation` 仍为 0；
   只有 `System.gc()`（Pause Full）才把它推到 1、2。
   → 泄漏检测永不触发（既不误报也不报警）。阈值检测（85%）那一支不受影响，是能工作的。
3. **可行替代判据（已验证）**：`oldGenPool.getCollectionUsage().getUsed()` 在 G1 Old Gen 上
   `collectionUsageSupported=true` 且持续更新；泄漏场景中"GC 后地板"从 304MB 单调抬升到 457MB，
   全程无 Full GC。健康场景地板稳定。注意首样本有噪声（出现地板>当前占用的读数），
   实现时应做平滑/取窗口最小值，别拿单点比。

## 追加：泄漏判据选型实验（先验证再实现）

候选判据（都用「GC 后地板」= `oldGenPool.getCollectionUsage().getUsed()`，该信号在 G1 上可用且会更新）：
- A：同一窗口内「前 1/3 中位数 vs 后 1/3 中位数」
- B：同一窗口内「前半窗最小值 vs 后半窗最小值」+ 要求窗内出现过回落
- C：**相邻两个等长基线**的地板中位数比较 + 要求跨度内出现过 ≥3% 回落

实测（JDK 24 + G1，-Xmx512m，探针 1s 采样，20 样本/基线）：
- A/B 在健康锯齿负载下**误报**（t=6..27 连续判泄漏）：窗内前后段相隔太近，
  老年代在两次回收之间的自然增长（约 9% of max）就超过了 10% 阈值 → **不可用**
- C 在同一负载下 **0 次误报**（地板 267MB 稳定，抬升 +0.0%～1.1%）；
  真泄漏负载（3MB/tick 单调增长）**31 次命中**（地板 257→322MB，抬升 +25%）→ **采用 C**

配置键：`leakDetection.baselineMinutes`(10) + `floorGrowthPercent`(10)，
移除 `windowMinutes` / `gcRecoveryThreshold`；`getFullGCCount()` 与 `MemorySample.fullGCCount` 一并删除
（G1 上恒 0，见前文）。
探针：/tmp/leakprobe/{RulePicked,RuleBase,CfgCheck}.java

教训：写场景脚本本身也要自检——RuleBase 第一版 `live`/`cycle` 双重引用，
"健康锯齿"其实是单调泄漏（98% OOM），差一点据此得出错误结论。

## 追加：完成用户的 JStatusAPI 重构（BanApi 数据转换 + 缓存适配）

用户已完成类继承重写（`JStatusApiSubhandler` 抽象 + `subhandlers[]` 声明式注册），
剩余任务：BanApi 的 `List<SConfig>` → `JSONArray` 转换，以及 BanApi / PhApi 的缓存适配。

### 做法
- **缓存放进基类**（声明式）：`JStatusApiSubhandler.cached(cacheKey, Supplier<JSONObject>)`
  + `cachedAt(cacheKey)`；命中只刷新 `retrieved_at`，重建时写 `retrieved_at`/`expires_at`。
  TTL 取 `CONF.cache()`，`<=0` 时不缓存。三个子端点（Ph/Ban/Status）全部改用该设施，
  删掉 WebStatusAPI 里原来私有的 `cache` 内部类（避免两套缓存实现）。
- **缓存键必须按请求区分**：Status 固定键 `"status"`；Ban 用 target 列表排序后 join（全量为 `*`）；
  Ph 用原始 payload 字符串。**单槽缓存在多参数端点上会串数据**——实测 `payload=A` 后
  立刻 `payload=B` 若共用槽位就会返回 A 的结果。
- **BanApi 转换**：`entryToJson(SConfig)` / `entriesToJson(List)`，字段
  target/type/banned/reason/op/create/expire；`type` 仅在条目自带时输出
  （枚举全部封禁时才有 ip/player）。顺手把错误的
  `org.jose4j.json.internal.json_simple.JSONArray` 改回 `org.json.simple.JSONArray`。
- **配置键纠错**：`CONF` 读的 `JStatusAPI.cors` / `JStatusAPI.whitelist` 与配置里的
  `cors-allowed` / `white-mode` / `ph_list` 不符（历史遗留，因默认值恰好都是 `*`/`true` 而没人发现）；
  已改对，并让 WebPhAPI 的名单检查走 `CONF`（解耦合）。
