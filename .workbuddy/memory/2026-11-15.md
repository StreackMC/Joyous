## 修正 @since 虚标（75 个文件）

问题：pom 是 0.4.0、最新 tag 是 0.3.0，但 75 个文件的 Javadoc 写着 `@since 0.6.0/0.7.0/0.8.0/0.9.0`——
这些版本根本不存在（pom 历史只到 0.4.0）。

溯源：`0.6.0` 来自 `1b7dc83 迁移到SConfig`（那是 **StreackLib** 的版本，被当成插件版本）；
`0.7.0` 来自 JwardChest 落地提交、`0.8.0` 来自 JSell 落地提交、`0.9.0` 是我上一轮的三个新类。

判定方法（可复用）：对每个文件 `git log --follow --diff-filter=A` 找创建提交，
再 `git show <commit>:pom.xml` 读当时的版本号 —— 那就是它真正随哪个版本发布。
不能用「文件首次出现在哪个 tag」判断：`952b1ef` 把 JSell 文件挪进子目录，路径变了会误判。

结果：75 处全部改写（0.6.0→0.2.0 ×1；0.7.0→0.3.0 ×18、→0.4.0 ×37；0.8.0→0.3.0 ×12、→0.4.0 ×4；
0.9.0→0.3.0 ×1、→0.4.0 ×2）。现分布：0.0.1(10) / 0.0.2(2) / 0.2.0(6) / 0.3.0(48) / 0.4.0(43)，
全部对应真实版本。旧值（0.0.x/0.2.x/0.3.x）复核过，与创建时的 pom 版本一致，未动。

规则已写进 MEMORY.md：`@since` 只能填已存在 tag 或当前 pom 版本，pom 是唯一版本源。

## 新增：JSell 出售流水（文本账）

问题：JSell 只在控制台 warn 出错、销量写数据库，**没有任何可对账的流水**，而 Entroprix 有
`plugins/Joyous/logs/Entroprix/yyyy-MM/dd.txt`。

- 新增 `utils/AsyncDailyLog`：单线程守护线程排队写、按天切文件（`<root>/yyyy-MM/dd.txt`）、
  每行 flush、`close()` 幂等且先排空队列。刻意**不注册 JVM shutdown hook**（每行已 flush，
  强杀最多丢一行；注册反而在插件重载时留钩子）。
- 新增 `JSell/data/SellLog`：固定列序 `时间 | 动作 | 玩家 | UUID | 分组 | 内容 | 数量 | 金额 | tx`，
  动作为 `SOLD` / `REFUND` / `FAILED`。写入点只有 `SellService.commit()`：
  钱发出后（`markStatus(PAID)` 之后）逐条 `Sale` 记一行，退款记一行，半途异常记 `FAILED`；
  没配数据库的降级路径也记（tx 写 `no-db`）。
- 配置 `JSell.log.enabled`（默认 true）/ `JSell.log.dir`（默认 `logs/JSell`）；
  启动日志会打印「出售流水 logs/JSell」或「已关闭」。
- 为可测性把 `SellLog.sold` 拆出「玩家名 + UUID 字符串」的重载，`SellLog.init` 拆出显式参数版本。

验证（临时自检，12 项全过后删除）：落盘路径 `yyyy-MM/dd.txt`、一 Sale 一行、列序/金额/分组/事务号、
关闭时不落盘、异步 50 行全落且顺序不变、关闭后写入被忽略、`close()` 幂等。
真机正常 `stop` 关服 exit=0，无 `SellLog` 相关异常。

⚠️ 自检第一版把「200 金币」写死，测试服 `unit.name` 是 `Scores` 才暴露——断言里要用
`JSellMain.CONF.unitName()`，不要硬编码可配置的文案。

## JSell 存档改为一组一文件（`models/JSell/groups/<组名>.yml`）

诉求：不要把各组数据全塞进 `items.yml`。原来改一条价格就整份重写，文件越大越容易写坏，
出问题也看不出是哪一组乱了。

- `SellEntryStore` 重写为「分组文件管理器」：`dir` = `models/JSell/groups`，一组一个 `format: 3` 文件；
  **组名 = 文件名，行内不再写 `group`**（两处说法冲突时不知道该信谁）。
- 只重写 `dirtyGroups` 里的文件；某组没有条目就删文件（组的边界就是文件）。`save()` 改分组时
  **两个组都要重写**。⚠️ 条目是可变对象，详情页改分组时 `save()` 拿到的就是表里那一份、
  `group` 已被覆盖 → 必须靠 `persistedGroups`（id→已落盘组名）快照判断「搬家」，否则旧组文件里那条删不掉。
- 文件名与组名：组名规范化后只含 `[a-z0-9_-]`≤32（跨平台安全）；Windows 保留设备名加 `_` 前缀
  （`con` → `_con.yml`）。判断「文件名是否规范」用 `fileOf(group).getName().equals(file.getName())`，
  ⚠️ 不能拿组名直接比：`con.yml` 与 `_con.yml` 都能读成组 `con`，少判一步会同时留两个文件 → 重载时
  「复活」已经删掉的条目。
- 迁移：`items.yml`（v2 的 `entries` 带 group / 0.8.x 的 `items` 整条 Base64）读出后按组拆分写盘，
  再改名 `items.legacy.bak`。**有解析失败记录时不改名**（改名虽不丢数据，但会让那几条彻底从服务里消失，
  管理员还以为迁移成功了）。载入顺序：先读 `groups/*.yml`，再并老存档，**同 id 以分组文件为准**，
  最后按 `createdAt` 排序入表（让「同代价取先登记」与文件顺序无关）。
- `entryStore` 字段与 `new SellEntryStore(...)` 之前在工作区里被删了一半（编译不过），一并补回。

验证（临时探针，跑完删）：
1. `SConfig` 写盘探针：新文件 `reload()` 不抛异常、`putList(无点键, List<Map>)` 能新建/覆盖、注释保留、
   空列表写成 `entries: [\n  ]`（所以空组要删文件）。
2. `SellEntryStore` 文件层探针（不碰 ItemStack，不需要服务端）：`fileOf` 映射（大小写/空格→规范化、
   `con`→`_con.yml`、`all`/空→`default`）、`rawGroupName`（`_con.yml`→`con`、非 yml→null）、
   非规范文件名能读入并写回规范文件、坏条目只记账不炸、老存档全坏时不归档、空老存档正常归档。
3. `mvn -o clean package` 通过。
- 未做：真机（需 Paper 服务端 + 真实 NBT 物品）验证「有内容时的拆分与写回」，留给用户实测。

### 补：旧存档只兼容 Base64 列表（0.4.0 未发版，不留中间格式分支）

用户定调：`format: 2` / `entries` 带 `group` 那版是开发期中间态、从未发版，**不需要兼容**。
- `readLegacyFile()` 只认 0.3.0 的 `items` 列表（一行一条整条 Base64 → 全归 `default`）；
  `decodeRow` 去掉 `readGroupKey` 参数（组名只认文件名）。
- 遇到「`items` 为空但 `entries` 非空」= 中间格式：报一次警告、**原样保留不归档**（不静默吞掉）。
- `FORMAT_VERSION` 从 3 降回 2（旧存档没有这个键，2 = 一组一文件）。
- 归档处的重复警告一并去掉：`!readable` 时静默返回（原因已在读取处报过），只有「有解析失败」才提示半迁移。
- 探针复验：中间格式 → items.yml 留、无 bak；坏 Base64 → 留；空列表 → 归档；分组文件坏条目只记账。
