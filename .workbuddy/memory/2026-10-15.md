# 2026-10-15 JwardChest：数量分布对齐

## 问题
用户问「物品可抽出数量满足什么分布？」——上一轮我把结果组总条数做成了**确定值（Σ上限）**，
只有各品质内部的配额是随机分摊，语义不自洽（既有 min/max 又恒等于 max）。

## 结论（已实现）
凡是「在 下限~上限 之间取一个整数」的地方，统一走新的 `WardDistribution`：

| 位置 | 区间 | 默认分布 |
|---|---|---|
| 结果组总条数 | 各品质下限之和 ~ 上限之和 | uniform（离散均匀） |
| 单条结果的物品数量 | 条目的 最小数量 ~ 最大数量 | uniform（离散均匀） |

- 三档：`uniform` 均匀 / `low` 偏小 / `high` 偏大；`curve` 为曲线指数（仅 low/high，1.0=线性）
- 配置键 `JwardChest.draw.count-distribution|count-curve|amount-distribution|amount-curve`
- **总条数下限强制 ≥1**（容器有格子时），避免"下限没设"时抽出一个空箱子；
  想让某品质「一定有 N 条」就设它的最小抽出数量
- 全 0（不限量）分支不变：按容器容量抽满

## 实现要点（易踩的坑）
`pick()` 用 **`floor(shaped * (span + 1))`** 而不是 `round(shaped * span)`：
后者会让区间**两端各只拿到半个桶**，导致最小/最大值出现概率只有中间值的一半。
实测（6000 次，[1,5]）：uniform → 1208/1210/1210/1195/1177（端点正常 ✓）

## 真机实测（Paper 1.21.11，临时自检块，验完已删）
- uniform [1~5]：1208/1210/1210/1195/1177，均值 2.99
- low(curve=2)：2609/1167/869/730/625，均值 2.27
- high(curve=2)：642/721/853/1125/2659，均值 3.74
- 总条数（下限和 0 / 上限和 10 / uniform，400 次）：1~10 各约 40 次 ✓
- 物品数量（1~5 / uniform）：1220/1172/1193/1166/1249 ✓
- 零异常；`/jc info` 新增一行「数量分布：总条数 uniform，物品数量 uniform」；
  上下限编辑界面与 lore 也显示了分布与区间

## 2026-10-15（续）正态分布 + 分布搬进容器设置 + 子界面 Esc 返回主界面

### 1. 新增 `normal`（截断离散正态）
- 按 `exp(-½((i-μ)/σ)²)` 给区间内每个整数算权重再抽取；**不是**"取正态再夹到区间"
  （后者会在两端堆出一块被压扁的概率，看起来像端点突变）
- `σ = 跨度 / (2 × curve)`，曲线指数越大越集中在中间（curve≈3 时 ±3σ 铺满区间）
- 真机实测（6000 次）：`normal [1~5] curve=2` → 290/1491/2405/1475/339，均值 3.01 ✓
  `normal [1~64] curve=3` → 均值 32.8、端点 1:1 2:8 63:1 64:2、中点 32:242 33:247 ✓

### 2. 分布从全局 config 搬进「容器设置」
- 落到 `WardProfile`（4 个字段：count/amount × distribution/curve），YAML 键 `profiles.<uuid>.draw.*`
  （写的时候仍是**两段路径 + 自组装的嵌套 map**，绕开 SConfig 读写不对称）
- 编辑界面新增「数量分布」按钮（主界面槽 17）→ 9 格子界面：
  槽 0/1 = 总条数（分布/曲线），槽 7/8 = 物品数量（分布/曲线）
  左键下一个 / 右键上一个 / Shift+点击 输入精确值；曲线 ±0.5，夹取到 1.0~10.0
- 界面上带**形状预览**（9 段 `▁▂▃▄▅▆▇█`）：直接**用同一个 `pick()` 采样**再统计，
  所以预览与真实行为必然一致（固定种子，同配置每次形状相同）
- `config.yml` 里的全局 `draw:` 段删掉了（防止和容器自身设置打架），换成一段指向编辑器的说明
- ⚠️ 兼容性：旧的全局配置键失效；已有容器不受影响（默认 uniform/2.0）

### 3. 子界面 Esc/E 返回主界面
- `WardListener.backToEditor`：子界面（容器类型/行数、上下限、数量分布、待选物品）关闭后
  **延迟一刻再判断「此刻是否还开着我们自己的界面」**——子界面之间的跳转本身也会触发关闭事件，
  那时不该再叠一次开界面；只有玩家真按 Esc 关掉的（此刻什么都没开）才回主界面
- 待选物品界面例外：只回主界面、**保留工作副本**（改动仍要点「保存」才生效），提示语单独一条；
  这样不会因为 Esc 而静默丢改动
- 正在等待聊天栏输入时（`chatInput.isWaiting`）一律不发提示、不跳转——那是我们自己关的界面

### ★★ 本轮最大的坑：IDE 的错误桩类 + 假成功的构建
- 症状：真机上 `java.lang.Error: Unresolved compilation problem: Duplicate local variable drawObj`
  来自 `WardProfile.readFrom`，但本地 `mvn package` 显示成功
- 根因两条叠加：
  1. **VS Code 的 Java 语言服务（jdt.ls）把带编译错误的类写进了 `target/classes`**
     （ECJ 会产出"能加载但一调用就抛 Error"的桩类）；
  2. **Maven 的增量编译看时间戳，认为 class 比 java 新就跳过重新编译** → 打包"成功"，
     jar 里装的却是桩类。所以「编译不过」被完全掩盖了
- 教训：
  - 改完代码必须 **`mvn -o clean package`**（不能只 `package`），
    并**验证产物**：`unzip -p target/*.jar '*.class' | grep -c "Unresolved compilation problem"` 必须为 0
  - 真机起服如果报 `Unresolved compilation problem`，第一反应就是"产物是脏的"，先 clean 重建
- 另一个假成功：`mvn ... | head -20; echo $?` —— 管道退出码是 `head` 的；
  而且 `${pipestatus[1]:-$?}` 只有 zsh 有 `pipestatus`，在 bash 下**静默退化成 `$?`=0**。
  正确做法：`mvn ... > /tmp/build.log 2>&1; echo $?` + `grep -c "BUILD SUCCESS"`

## 2026-10-15（续 3）紧急窗口一并改玻璃板颜色 —— 顺手把占位 API 收敛成「帧」

用户目标：进入 urgentTime 时**玻璃板材质**也要换色（原来只换文字颜色）；
同时抱怨「API 设计太冗余，改不动」——同一组 `(rarity, 剩余, 总时长)` 被算了三遍
（文本一遍、紧急判定一遍、材质又要一遍），调用方还要人肉保证「文本变的那一刻材质也变」。

### 做法：`WardGui.Frame`（record：material + text）
- **材质与文本同一次计算产出** ⇒ 紧急时两者必然同步，调用方不再需要单独问「现在紧急了吗」
- `prefilterFrame(rarity, remain, duration)` —— 粗筛阶段（带秒数，整秒量化）
- `slotFrame(rarity, remain, duration)` —— 逐结果阶段（不带秒数）
- `searchingPane(Frame)` —— 由帧构造物品
- 私有：`frameOf(..., withSeconds=true/false)`、`seconds()`、`isUrgent(remain, duration)`、
  `urgentPane(rarity)`、`pane(...)`
- **删掉的冗余面**：`searchingPane(rarity, remain, duration)`、`searchingPaneText(text, rarity, urgent)`、
  `searchingText(...)`、`slotSearchingText(...)`、公开的 `isUrgent`；`isUrgent` 原来的 `rarity` 参数
  其实从未被使用，一并去掉
- 控制器：`push(Search, Inventory, int slot, WardGui.Frame)`，缓存由 `String[] textCache`
  改为 `WardGui.Frame[] frameCache`（`forgetTextCache` → `forgetFrameCache`）。
  **比较一帧 = 比较整格画出来的样子**，比只比文本更准确（万一将来材质与文字脱钩也不会漏发）

### 配色（沿用五档珍惜度：普通白 / 稀有绿 / 典藏紫 / 珍贵金 / 绝世红）
`urgentPane()` 用 **enum switch**（原来是 `switch (rarity.id())` 字符串匹配，写错不报错）：
COMMON→WHITE、RARE→LIME、COLLECT→PURPLE、PRECIOUS→**ORANGE**、MYTHIC→RED。
⚠️ 普通档的紧急色就是白色，与平时白玻璃板相同（配色本身的必然结果）→ 该档只有名字颜色变，
   已写进 config.yml 注释与代码注释；若要它有区别，改 `urgentPane` 一处即可。

### 教训
- **`record` 是收敛这类「一组参数反复算」API 的好工具**：把「一次计算的全部产物」打包，
  用 `equals` 天然充当缓存键，调用方不必知道内部有几个字段、也不会漏比较。
- 用 `switch (enum)` 代替 `switch (id())` —— 字符串 case 拼错只是静默落到 default。
